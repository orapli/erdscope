01

製品を一度使う

コードより先に、入力と成果物を手で結びつけます。所要目安15〜25分。

README.ja.md

対応入力、代表ユースケース、Viewerで何ができるかを把握します。

「この製品は何を統合し、何を出すのか」を一文で言える。
docs/manual.ja.html

UIの名前と利用者向けの意味を先に覚えます。特にLayout、Direction、Auto-expand、Focus。

Layoutと関係探索Directionの違いを説明できる。
examples/README.md

SQLiteのコミット済み例で、ゼロセットアップの入出力を確認します。

生成HTMLがサーバー不要の自己完結ファイルだと分かる。
python3 erd.py demo --no-open
python3 erd.py sqlite:///examples/demo_shop.db -o /tmp/erdscope-reading.html
02

単一ファイルの仕組み

このリポジトリ固有の「読み方」を決める最重要ステーションです。

tools/build_single_file.py

MODULES がPython断片の実行順です。ディレクトリは base.py を先頭に展開されます。

分割ファイル同士がimportせず、同一モジュールのglobalを共有する理由が分かる。
src/erdscope/exporters.py

HTML_TEMPLATE sentinelがviewer埋め込み位置です。Excel出力もここにあります。

viewer.htmlがどこでPython文字列になるかを指せる。
pyproject.toml

配布対象が erd という単一py-moduleであることを確認します。

なぜ src/erdscope が通常のPython packageではないか説明できる。
絶対に守る編集境界

erd.py と docs/index.html は生成物です。Pythonは src/erdscope/*.py、Viewerは src/erdscope/viewer.html を編集します。

python3 tools/build_single_file.py          # 生成
python3 tools/build_single_file.py --check  # sourceと生成物の一致確認
python3 docs/gen_demo.py                    # docs/index.htmlを再生成
03

IRとマージ規則

入力形式の違いを吸収する中間表現と、フィールド別の権限を理解します。

src/erdscope/ir.py

ProviderResult、association provenance、viewer向けlegacy flagの最小契約です。短いので全読します。

db_fk / declared / manual / inferred の由来を説明できる。
openwiki/domain/schema-merge.md

physicalとlogicalの権限、疎なfragment、関連の同一性、config操作の意図を先に言葉で読みます。

「後から来た入力が常に全部勝つ」わけではない理由が分かる。
src/erdscope/merge.py

merge_ir()、association_key()、DB FK reconciliationが実際の契約です。

Phase Aの同一性マージとPhase BのDB FK吸収を分けて説明できる。
tests/test_merge_ir.py

文章では曖昧になりやすい同率・欠落・drop・重複関連の境界例をテストから学びます。

変更するフィールドに対応する既存テストを見つけられる。
境界主な形注意点
ProviderResult{source, tables, warnings}疎なfragment。欠落は「空」と同じではありません。
Merged IRtables / columns / indexes / associations構造化provenanceとsourcesを保持します。
Viewer payloadlegacy flags + notes + groups内部provenanceを直接漏らさない互換境界です。
04

入力レイヤー

すべての入力実装を読む必要はありません。registryと代表1本を読んでから横展開します。

db/base.py

DBAdapter registry、plugin seam、共通IR builderを読みます。

URL schemeからadapter classへ到達する流れを追える。
frameworks/base.py

FrameworkOverlay、priority付き自動検出、FK推論の基礎です。

untyped --models のfirst-match規則を説明できる。
sources.py

legacy modelsとtyped sourcesを一つのInputSpec列へ正規化します。

rails.project macroが何へ展開されるか追える。
providers.py

DB provider、config layer、notes/groupsの意味検証が集まります。

構文検証とfinal IRに対する意味検証の違いが分かる。
db/sqlite.py

最小で追いやすいDB adapterの代表として先に読みます。

adapterが最終形ではなくProviderResult用tablesを返すと分かる。
frameworks/sqlalchemy.py

AST検出、base除外、列と関連の両方を持つ複合的なoverlay例です。

静的解析の限界をwarning/configで補う設計が分かる。
派生実装のおすすめ順

SQLite → MySQL/PostgreSQL → Rails schema → SQLAlchemy → Rails/Django/Prisma/Laravel。最初から全parserを精読しないでください。

06

Viewerの内部

7,000行を超えるファイルを上から通読せず、状態 → 表示集合 → 配置 → 描画 → 編集・操作の順で分割します。

最重要の分離

getDisplayTables() が「何を見せるか」、layoutAll() が「テーブルをどこへ置くか」、routeEdge() が「線をどう通すか」を決めます。相互に責任を逆流させません。

読む順viewer.htmlの目印理解する内容
6-ADATA〜getDisplayEdges()永続状態、ROOT/AUTO/KEPT、focus、表示集合。
6-BcalcSize()〜layoutAll()実ノード寸法、Vertical/Horizontal、Auto候補評価、衝突補正。
6-CrefreshView()〜drawNode()再配置条件、fit、SVG描画、group frame。
6-DedgeCard()〜drawEdge()straight-first routing、marker、through label、self loop。
6-Eselection〜details/undo選択、focus、ban/promote、notes、undo/redo。
6-FbuildExportSvg()〜PNG画面とexportの経路・marker・group再利用。
6-GSchema Grid〜proposed schema / config export表形式の探索、notes、ToBe編集、永続化、Discard、Config/HTML export。
6-Hdrag〜control sync / views / shareincident edgeだけの再描画、UIイベント、views/share/state。

現在のLayoutモデル

Vertical

互換デフォルト。BFS depth row、branch順、isolated shelfを維持します。

Horizontal

hubの左右へdepth-1 branchを負荷分割し、子孫をowner側に保ちます。

Auto

両orientationの有限候補を最終補正後に比較し、実質同点ならVerticalを選びます。

現在のEdge routingモデル

1 straightclearなら必ず優先
2 one bendH→V / V→H
3 dogleg外側laneで2折り
validate8px障害物余白
endpoints内部通過を棄却
fallback最後だけBézier
labelpill全体を退避
  • multi-association数を線の曲がりで表現しません。
  • self relationだけは従来のcompact loopです。
  • drag中はincident edgeだけを差し替えます。
  • group frameは通常のtable obstacleとは別扱いで、新しく自動配置するtableに対してだけ障害物になります。
  • Layout変更はoverviewだけ。Focus配置は別契約です。
  • 同じ入力・寸法・viewportなら決定的である必要があります。
07

テストを仕様書として読む

正確な境界条件は、説明文よりfixtureとassertionに現れます。

test_characterization.py

既存出力のshapeと決定性。大きな変更前の土台です。

test_pipeline.py

入力レイヤーからviewer payloadまでの統合境界です。

test_e2e.py

実際の生成HTMLをChromiumで操作します。Viewerの挙動仕様として読みます。

Viewer E2Eのおすすめ読解順

  1. TestLayoutOrientation — 状態、UI、focus、undo境界
  2. TestHorizontalLayout — branch ownershipと左右負荷分割
  3. TestAutoLayoutOrientation — viewport別選択とtie-break
  4. TestEdgeRouting — 直線、dogleg、障害物、label、drag、export
  5. TestAutoTidyLayoutQuality — groupとresidual overlapの難所
  6. TestClientJS — 選択、drag、align、viewportの横断回帰
  7. TestSchemaGridModal と test_schema_grid / test_notes / test_proposed_schema — 表形式UI、編集、永続化、export
python3 -m unittest \
  tests.test_e2e.TestLayoutOrientation \
  tests.test_e2e.TestHorizontalLayout \
  tests.test_e2e.TestAutoLayoutOrientation \
  tests.test_e2e.TestEdgeRouting -v
Optional dependencyを見落とさない

Playwrightがない環境ではE2Eがskipします。「全テストOK」と「ブラウザ確認済み」は同義ではありません。

Viewer変更の標準手順

# 1. focused browser tests
python3 -m unittest tests.test_e2e.TestEdgeRouting -v

# 2. generated artifacts
python3 tools/build_single_file.py
python3 docs/gen_demo.py

# 3. consistency and regression
python3 tools/build_single_file.py --check
python3 -m unittest tests.test_characterization.TestDemoHTMLDeterminism -v

git diff --check
差分レビューで毎回見ること

生成物だけの手編集、無関係なvertical/focus挙動、順序依存の追加、非決定性、optional dependencyの無言skip、古いstate/share payloadの互換性。
